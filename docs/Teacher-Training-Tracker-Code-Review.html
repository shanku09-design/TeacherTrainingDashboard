Teacher Training Tracker
Code Review

A source-level review of the dashboard demo, its role journeys, data handling, uploads, reporting, and deployment. This review separates what works for a guided demonstration from what must be in place before real training records are used.

Review date · 15 October 2026Scope · application + deploymentMethod · static source inspectionAudience · stakeholders and delivery teams
Management takeaway

Good foundation for a controlled product demo using synthetic data. The repository identifies the app as a client-side prototype. Persona login, uploads, saved records, exports, and certificates should not be presented as production controls or live operations.

01 · Executive view

The application presents the training lifecycle clearly: programme setup, batches, attendance, learning resources, assessments, feedback, reports, progress, and certificates. The largest gap is the boundary between a convincing interface and a system of record. Several visible controls currently show sample or confirmation behavior without storing a business record.

03 · How the demo works today

Step through the current session. The interaction is useful for presentations, while identity and most application data remain in the browser.

→→→→
Step 1 · Select persona

Login pre-fills a demo account for Admin, Trainer, or Trainee to make a guided walkthrough quick.

Step 2 · Create session

auth.js generates token-shaped values in browser storage. No server verifies the identity.

Step 3 · Check route

app.js checks the stored role before rendering. A browser owner can alter this client-side state.

Step 4 · Render samples

The dashboards use seeded JavaScript records. Attendance and most workflow changes remain in memory.

Step 5 · Reload or sign out

Sign out clears demo session keys, but in-memory changes are not a durable training record.

04 · Prioritized findings

Use the filters to focus the discussion. Source references identify where engineering can start.

8 findings

F-01 · Browser persona login is not real authentication

Critical before production

The login page pre-fills personas, auth.js creates the session, and the router checks the role in browser JavaScript. There is no server identity verification or server-side permission check. A user can modify client state and reveal routes or trigger client actions. The project README explicitly calls this demo-only authentication.

auth.js · 3-17app.js · 674-683codebase/README.md · Demo scope

Impact: Do not use this mechanism to protect real trainee records, certificates, exports, or admin operations. Action: Add server-verified identity, role/project/batch authorization on every API request, and a visible Demo data label.

F-02 · Trainer “Upcoming batches” points to an Admin-only report

High · confirmed defect

The Trainer dashboard tile opens /reports/batches. The router classifies all /reports pages as Admin-only, so the permission check redirects the Trainer back to the Trainer home.

app.js · 583, 678-682

Action: Link to a Trainer-scoped batch list, or expose a report route that returns only batches assigned to that trainer. Verify the destination under each persona.

F-03 · Attendance and learner activity do not persist

High · pilot blocker

Attendance uses S.attSaved; assessment and feedback use in-memory objects; registration increments a generated batch counter. Refreshing the page reconstructs the seeded data. These paths do not write server audit records.

app.js · 167, 604, 645, 650, 670

Impact: A “saved” action can disappear on reload or another device. Action: Save to an authenticated API, return a server timestamp and record ID, and append an audit event.

F-04 · Upload and import controls simulate success

High · core workflow gap

Batch validation ignores spreadsheet bytes and renders fixed example rows. Resource upload records only metadata such as name and size; the selected file is not sent or stored. Opening it later produces a generated sample preview.

app.js · 505-516app.js · 552-566

Action: Parse the actual file, show row-level validation, upload to protected storage, and validate extension, MIME, signature, size, and malware on the server.

F-05 · Export and certificate actions do not create deliverables

High · expectation mismatch

“Download CSV” opens a preview dialog. Excel/PDF show explanatory toasts. Template save also shows only a toast; minimum attendance is a placeholder. Trainee certificate availability is derived from sample completion flags and renders a sample card.

app.js · 242-245, 547-551, 651-655

Action: Label actions “Preview” until implemented. Approve eligibility rules, issue verifiable certificates from server-confirmed records, and audit issue, reissue, correction, and revocation.

F-06 · Seeded figures and a fixed date can be mistaken for live MIS

Medium · trust and freshness

Schools, batches, attendance, and resource usage are generated from demo data. “Today” is a fixed date. The user report includes static login, failure, and OTP figures. This helps repeat a presentation but does not represent operating performance.

app.js · 19-22, 54-86, 126-139, 437-441

Action: Add persistent Sample data labels, put dates in a scenario config, and define live metric source, calculation, refresh time, and reconciliation.

F-07 · One global script owns almost the whole application

Medium · maintainability

app.js is about 121 KB and 701 lines. It combines sample data, calculations, route permissions, page templates, and handlers. Inline event attributes and global state couple unrelated pages. Sass token values are also partly repeated as hard-coded CSS custom properties.

app.js · entire filesrc/scss/main.scss · 1-10

Action: Split data, authentication, routing, shared UI, and persona pages into modules. Move event wiring to listeners and centralize design tokens.

F-08 · Deployment has no build or quality gate

Medium · release quality

The GitHub Pages workflow copies static files directly and does not compile Sass, lint JavaScript, validate links, run tests, or check accessibility. Bootstrap and the login font also load from external CDNs.

.github/workflows/deploy-pages.yml · 1-56codebase/package.jsonindex.html + dashboard.html

Action: Add a locked, repeatable install/build, route and authorization tests, accessibility checks, and a deployment smoke check. Consider local assets for network-restricted demos.

05 · Example improvements

The following examples illustrate how to close the largest gaps. They are design patterns, not drop-in code for the current static server.

Example A · Enforce ownership at the API

The server checks identity, role, batch assignment, and request data before it writes attendance.

Illustrative server-side pseudocode
async function saveAttendance(req, res) {
  const user = await requireAuthenticatedUser(req);
  if (!user.roles.includes("trainer")) return res.sendStatus(403);
  const batch = await batches.findById(req.body.batchId);
  if (!batch || batch.trainerUserId !== user.id) return res.sendStatus(404);
  const entry = await attendance.save({
    batchId: batch.id,
    date: validateTrainingDate(req.body.date),
    entries: validateParticipantMarks(req.body.entries),
    changedBy: user.id
  });
  await audit.append({ actorId: user.id, action: "attendance.saved", recordId: entry.id });
  return res.status(201).json({ id: entry.id, savedAt: entry.savedAt });
}

The important boundary is the server, which resolves the user and scope. A hidden Admin link is not an access control.

Example B · Make the CSV action a real download

After the server returns authorized rows, the browser can create a file. Production exports should still be permission-checked and audited.

Illustrative browser download
function downloadCsv(rows) {
  const csv = rows.map(row => row.map(csvCell).join(",")).join("\r\n");
  const file = new Blob([csv], { type: "text/csv;charset=utf-8" });
  const url = URL.createObjectURL(file);
  const link = document.createElement("a");
  link.href = url;
  link.download = "training-report.csv";
  link.click();
  URL.revokeObjectURL(url);
}

Until that exists, name the current action “Preview CSV”.

Example C · Keep demo data clearly labeled

Use a persistent notice on every role dashboard, report, and preview so sample figures cannot be confused with live operations.

Illustrative interface label
<aside role="note" class="data-notice">
  Demonstration data. This dashboard is not connected to live training records.
</aside>

06 · Recommended production request flow

A browser remains the user interface. The backend verifies identity and owns authorization, persistence, validation, and audit history. Step through an attendance request.

→→→→
Step 1 · Send request

Trainer sends a batch ID, date, and attendance marks over HTTPS. The page shows pending until the server responds.

Step 2 · Verify identity

Identity service verifies the session and resolves a stable user ID. The client does not invent the user's role.

Step 3 · Authorize scope

API confirms Trainer role and batch assignment, then validates date, participants, duplicate submissions, and business rules.

Step 4 · Save record

Database stores stable IDs and server timestamps. Retries should be idempotent and avoid duplicate attendance entries.

Step 5 · Confirm and audit

Server writes an audit event and returns a saved result. The UI can show the timestamp and recover the same record after reload.

07 · Delivery roadmap

Close the authorization and data-trust gaps before onboarding real participants. Keep this static prototype available as a clearly labeled presentation build while a server-backed pilot is prepared.

Fix the demo journey

Correct the Trainer batch link. Label sample data and replace fake upload, export, and save confirmation with “Demo preview” labels.

Approve business and security rules

Confirm identity provider, role/project scope, attendance and completion rules, certificate eligibility, upload contracts, retention, and audit expectations.

Build the system of record

Add authenticated APIs, durable project/batch/participant/attendance records, secure resource storage, validation, transactions, backups, and change history.

Connect real workflows

Implement batch imports, roster approval, attendance, assessments, feedback, resource upload, exports, and certificate issuance using server-confirmed data.

Gate each release

Add lint, repeatable build, route and authorization tests, upload validation tests, accessibility checks, UAT, and security review before pilot deployment.

Stakeholder ownership

Business: approve rules and permissions. Engineering: identity, API, database, persistence, and secure uploads. QA: map requirements to saved results and evidence. Operations: approve hosting, backup, retention, and support ownership.

08 · Readiness and sign-off

Guided demo

  • Explain the sample-data and demo-auth boundary.
  • Fix or avoid the Trainer upcoming-batches tile.
  • Describe upload/export/certificate actions as previews.
  • Use synthetic data and prepared browser state.

Pilot gate

  • Server identity and role/project authorization.
  • Durable records with audit and reconciliation.
  • Real uploads and exports with validation.
  • Approved certification rules and verifiable issuance.
  • Automated quality checks, UAT, privacy, and security sign-off.
Conclusion

This is a strong interactive prototype and a useful starting point for stakeholder feedback. Treat it as a demo build until Critical and High findings are closed and pilot readiness is approved.
